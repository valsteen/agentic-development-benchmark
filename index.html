Benchmark: autonomous coding across AI models

Can a cheaper coding model finish useful work with limited supervision? This benchmark compares time, usage cost and the code delivered for one Git integration feature in a Python project. It includes Opus 5.5 high, Sonnet 5.5 high, Astra 6 low, Sol 6.1 high, Luna 6 medium/high/xhigh, Haiku 5.5 high/xhigh, and high configurations of GLM 5.3, GLM 5.3 Flash, DeepSeek V4.1 Flash and Kimi K3.

Each model started with the same detailed brief and repository guidance. It implemented the feature and arranged reviews in separate chats using the same model and effort. Corrections and reviews could repeat until approval or a report that it could not finish; costs include that whole workflow. One run per configuration was measured.

The later common checks found a false “change is integrated” answer in 13 of the 13 saved implementations. Luna 6 high remains the lowest token-price estimate at $0.92, with a 2/10 rating on those checks. DeepSeek V4.1 Flash high finished sooner with the same selected failures for $2.15 at token tariffs. GLM 5.3 high improved one check for $18.23. Kimi K3 high’s three reviews improved the change, but it still scored 1/10. Reviewer approval and the later code assessment are kept separate.

The task for each model

The task was to add a Git integration check to an MCP-based task orchestration tool (Pinboard). The check tells coding agents whether a reviewed change has reached a particular Git branch, helping them decide what work remains. A squash or rebase can change commit identities even though the work is there. The feature compares the reviewed change against the target by content, without changing the repository or the tool’s task records.

The tool is written in Python and developed by the author of this benchmark. It already had typed interfaces, tests, architecture documentation and repository guidance. Implementing the feature required changes to Git handling, choosing the stored revision to check, the MCP interface, failure handling, tests and documentation. Production additions ranged from 660 to 1,155 lines; test additions ranged from 543 to 1,095.

Each model received the same brief, including one contradiction requiring a human decision. It managed implementation, reviews and corrections using the same model and effort. Reviews took place in separate chats and could repeat until the model approved its work or reported that it could not finish. Separate checks followed after the models submitted their code. The costs include review and correction.

Choosing a model for similar work

If you are waiting for the result

Opus 5.5 finished in about 26 minutes for $16.65. Sonnet 5.5 took 38 minutes, but now costs $12.02 at current prices. Both left the same three reproduced failures on the later checks.

If the task can run while you are busy

Luna 6 high produced code, tests and documentation for $0.92 in 111 minutes. Medium took 77 minutes for $1.45, but left an extra false positive. DeepSeek V4.1 Flash high took 79 minutes for $2.15 with the same selected failures as high, though its run had an output-access problem. High remains the cheapest token-price result; the quality table shows what still needs fixing.

If failure handling matters to the task

Sol 6.1’s reviews led to fixes for cases the others missed, for $14.26. It took 144 minutes and still had a false positive. Astra 6 raised the brief’s ambiguity and completed a useful correction sooner, but still had bugs after spending $45.

With one run per configuration, these results suggest what to try; they do not establish a model ranking. For your own task, the extra human work needed to get a usable result may matter more than a small usage saving. Waiting may matter more when you cannot do something else in the meantime.

How the quality rating is calculated

A false “integrated” answer receives the largest penalty because it could cause the caller to skip work that still needs doing. A wrong failure diagnosis hides that the check could not inspect the target. Configuration dependence makes the same request behave differently across users. An unexpected error for malformed input loses the error response promised by the brief, but does not affirm that missing work is present.

The rating scores each remaining failure once per check. Corrected defects receive no penalty here; their contribution is described in the review table. Opus 5.5 high: 7 penalty points (3/10); Sonnet 5.5 high: 7 penalty points (3/10); Astra 6 low: 6 penalty points (4/10); Sol 6.1 high: 4 penalty points (6/10); Luna 6 high: 8 penalty points (2/10); Luna 6 xhigh: 6 penalty points (4/10); Haiku 5.5 high: 8 penalty points (2/10); Haiku 5.5 xhigh: 6 penalty points (4/10); Luna 6 medium: 12 penalty points (0/10); GLM 5.3 high: 6 penalty points (4/10); GLM 5.3 Flash high: 12 penalty points (0/10); DeepSeek V4.1 Flash high: 8 penalty points (2/10); Kimi K3 high: 9 penalty points (1/10). How those bugs could affect the caller

A false “integrated” answer could lead the next agent to skip work that still needs doing. Reporting unreadable Git content as ordinary absence has a different effect: it hides that the check could not inspect the target. The individual outcomes remain visible alongside the rating because the repair needed is different.

The cost and time figures include all implementation, review and correction work performed during the autonomous runs. The later checks show what those runs delivered and which defects remained. Their severity helps you judge what could happen if the bugs reached production. The checks were local; the code was not deployed. Finding and fixing bugs after a run would add costs beyond the comparison here.

Human input and time spent getting a result

The brief contained a contradiction: an empty change was supposed to return without Git, while the result also had to name the resolved target commit. Astra 6, Sol 6.1 and Haiku 5.5 high asked about it. They received the author’s answer from an earlier attempt: resolve the target, then skip the content comparison. The other configurations chose an interpretation without asking.

The benchmark runner passed back that earlier answer only after each model asked, so no new human decision was needed. There was no recorded human help with the implementation. Those clarification requests show that the models noticed the contradiction; they do not measure human reading or thinking time. In this case, asking was useful because it exposed a decision the brief had left unresolved.

Haiku 5.5 high paused three times for input. One pause incorrectly claimed the time allowance was exhausted; the response restated the actual remaining allowance. The other two sought direction on finishing the tests and preserving the brief’s failure contract. Only existing answers and requirements were relayed. Haiku 5.5 xhigh required no human exchange. These counts describe interruptions, not hours of human work saved.

When does a cheaper run save money?

Luna 6 high is the low-cost reference here: $0.92 for the recorded implementation, review and corrections. Think of it as the default you could use frequently, then ask whether paying more for another model saves enough human time to justify the difference. The figure uses API-equivalent costs; it does not predict a subscription’s quota consumption.

Suppose a more expensive model delivers an equally useful result with less human involvement. The chart asks how much that saved time would need to be worth to cover the extra AI cost. You choose the time saving; it was not measured in this benchmark.

At $100/hour, Opus 5.5 high needs to save just 9.4 minutes across the whole workflow to cover its extra $15.72: preparing the request, steering the agent, checking the result, reviewing and deploying. How much back-and-forth would fit into nine minutes?

Count time from everyone involved, including other reviewers. Waiting can count when it ties someone to an interactive session or prevents other useful work; value that time according to what it displaces. A background agent run while you do something else is not the same amount of human work.

A monthly AI allowance can run out while the work continues. If the rest then has to be done without agent help, the AI bill is capped; the human work is still being paid for.

Luna 6 high compared with Luna 6 xhigh

The higher effort setting added only $0.72 to the usage bill. The time difference was much larger: about 146 extra minutes. Luna 6 xhigh improved tests and documentation, but retained the shared mode and content-read defects. For this task, Luna 6 high looks like the more useful configuration to try first when you can wait and have a way to check the result.

Luna 6 medium compared with Luna 6 high

Medium finished in 77 minutes, about 30% sooner than high’s 111. It cost $1.45 rather than $0.92—about $0.53 more. The lower effort setting did not produce a cheaper run: it went through eight review attempts and seven intervening rounds, including one history-only retry, without asking for human input.

The final code retained high’s three selected failures and added a nested-directory false positive, taking the rating from 2/10 to 0/10. Medium’s speed may suit a task you can check cheaply, but this run gives no reason to trade high’s result for medium’s on cost or these quality checks. The rating describes this feature’s selected failure cases; it does not mean medium did no useful work.

Haiku 5.5 compared with Luna 6 high

How the benchmark worked

Task brief→Implement and verify→Same model reviews in a separate chat↔Correct and review again→Model reports its result

Each reviewer received the requirements in a separate chat, using the implementer’s model and effort. Separate chats keep the conversations apart, but the same model can still miss the same kind of bug. Separate checks of the saved code followed after each model finished. Required human decisions remained part of the task.

Every model started from the same version of the project and received a brief prepared earlier. Preparing the brief was outside the measurement, and the models were not asked to review it before starting. Each model managed its reviews and corrections, could ask for a human decision, and could report that it could not finish. Reviewers were given the brief so they could check the work against its requirements without turning every suggestion into more work.

The benchmark runner saved the outputs and passed back earlier answers only when the models asked the same question. It did not point out bugs or provide fixes. Some models made corrections themselves; others asked another agent to do them. Some left their tasks in the tool open. Those differences explain the work and cost; they are not scored as code quality.

Making the benchmark and report

I commissioned this benchmark and reviewed the agents’ setup and writing. Astra 6 medium ran the original six configurations. Sol 6.1 high drafted the report and coordinated the later Haiku 5.5, Luna 6 medium and Neuralwatt extensions.

The intended experiment let each model implement the feature and arrange its own reviews, asking for human decisions when needed. In the first attempt, Astra 6 reviewed every model’s work, and the workflow allowed only one correction round. That attempt was discarded. Its PRs remain as evidence, but its results aren’t included here.

A later run stopped near three hours. The agent described a 180-minute cutoff as an existing limitation and began discussing ways around it. The author kept asking where it came from.

The benchmark chat had chosen the cutoff itself. The author had not approved that choice. Tracing its origin changed the question: should that time allowance have been set at all?

Then the author requested cost and time broken down by review round. The initial answer made the evidence sound unavailable. The transcripts were still there, though, with timestamps and usage records. The agent eventually clarified:

“I just haven’t extracted them.”

There was still work to do. The agent went back to the transcripts and recovered useful estimates, with caveats. Some of them are in this report.

The resulting guidance changes ask agents to check where a limit comes from, say when they chose it themselves, and clear up a misunderstanding before proposing more changes. A separate behavioral harness exercised the explanation in small invented situations with real Sol 6 high replies.

Those replays caught a problem in the test: it expected agents to identify who chose the cutoff, but only told them who wrote the comment about it. After correcting the prompt, all four replays passed—two with the earlier guidance and two with the revised guidance. The replies identified the agent’s choice, explained the resource tradeoff and left the remaining decision with the human. Testing produced useful evidence and a better test; these few repetitions do not establish that one guidance version is better.

How the guidance was tested

The first batch produced eleven Sol 6 high replies across three versions of the guidance. Three cases were kept untouched until the final wording was frozen. Probes, replies, blind scoring and separate assessments cost $2.26 in recorded usage and returned within about 32 minutes, with the runner already built.

A follow-up produced thirteen more Sol 6 high replies for $2.89 within about 51 minutes. Nine used the existing cases; four used the corrected cutoff case. The follow-up had a one-hour/$10 allowance. Planned repetitions stopped when the prompt ambiguity was found, and the remaining replays checked the correction. Building the runner and reviewing the changes are outside both batches’ figures.

The earlier cutoff-attribution grades remain recorded, but the affected cases cannot establish failure to mention a fact the prompt did not supply. The repaired case is a different test condition, and was already familiar; its results cannot be pooled with the old grades or called fresh held-out evidence. Both guidance versions passed their two corrected replays. The comparison criteria require more repetitions before supporting a statistical claim. Here, “inconclusive” describes the comparison between guidance versions, rather than an absence of useful findings.

Other concerns survived inspection: one earlier reply using revised guidance drifted toward proposing another cutoff, and an important verification caveat appeared only in commentary. A scorer rationale in the first batch also conflicted with a maintainer identity supplied in the context. Checking the prompts, actual replies and grading assumptions exposed problems that a summary score would hide.

The constraint paragraph was visible in the recorded agent context, but some replies received only part of the surrounding instructions because tool output was truncated. The evidence report records those omissions. A separate reviewer checked the prompt repair and the reconciled evidence; Linux, macOS and duplication checks passed on that PR revision. Those checks cover the repair and reporting, rather than certifying better agent behavior.

For the person commissioning the work, there is something to practice too: catching these contradictions earlier. “Where does that limit come from?” and “What is still in the logs?” gave the agent something concrete to investigate. In these exchanges, those questions got the conversation further than another expression of frustration.

The author called the report’s first writing style “corporate tabloid.” There were headings like “What each run bought,” abstract accounts of events the author had just experienced, and paragraphs that all moved at the same pace. The headings had more confidence than the text offered context. Skimming past one could leave the next paragraph hard to place.

The editing focused on recognizable situations, visible points worth noticing, and internal terms and adjectives that added no information. “Established Python tool,” for example, suggested a reputation the report had not demonstrated. Describing what the tool does through MCP, and the tests and documentation already in the project, gave readers something they could check.

These adjustments also informed an update to the technical-writing skill, for future reports, RFCs and other technical documents.

Style instructions you can reuse

These instructions collect the adjustments made while editing this report. They can go into a writing skill or a prompt.

Write for the document’s actual readers and the decisions they need to make. Assume they may skim sections out of order. Use a conversational, factual voice. Preserve meaning, evidence and uncertainty.

Name who acted or made a decision when responsibility matters. Avoid ambiguous “we” and unexplained switches between “I” and “we.” Use first person where personal attribution helps the reader.

Make the opening sentence orient the reader without relying on the heading. Establish the situation and why it matters before adding detail.

Use headings that name the subject in ordinary language. Avoid “corporate tabloid” slogans, inflated drama and promises the text does not fulfill.

Make adjectives earn their place. Keep one when it explains a useful distinction. Replace vague claims of maturity, importance or reputation with concrete facts the reader can assess.

Translate internal terms into the actions, decisions or effects they describe. Keep precise technical terms when they give the audience useful context. Explain unfamiliar terms once, then use them consistently.

Think of attention as a dead man’s switch. Each next sentence should offer a useful connection, consequence, example, discovery or question. Balance the glue between ideas with points worth noticing. Do not make every sentence a headline or bury the important point in routine explanation.

Let sentence and paragraph lengths follow the material. Preserve who did what and what changed. Avoid giving every paragraph the same claim–explanation–lesson pattern.

Give each sentence one main job. Put meaningful inventories in bullets, tables or separate sentences rather than compressing several distinctions into one sentence. Keep connected prose for relationships and reasoning.

Make recommendations follow from the evidence. Distinguish observations, interpretations, proposals and unanswered questions. Present useful estimates and qualitative assessments with their assumptions and limits. Do not dismiss useful evidence because a more direct measurement is absent, or make a claim more certain to give the story a neat ending.

Preserve identifiers, versions, dates, configurations and scope when they change how a claim should be interpreted or reproduced. Put units beside quantities. Include these details where they help the reader, without repeating them mechanically.

Read the whole draft, including captions, tables and expandable details. Try a section without its heading. Read the sentences around each important point aloud. Cut padding, clarify the concrete situation and vary the rhythm where attention drifts.
